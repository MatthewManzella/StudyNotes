JSON Columns, Migrations & Replication

2026-09-12

JSON/JSONB Columns

Store semi-structured data in a column and query into it directly — useful when a field's shape varies row-to-row and doesn't justify its own tables.

CREATE TABLE events (
  id serial PRIMARY KEY,
  payload jsonb
);
INSERT INTO events (payload) VALUES
  ('{"type": "click", "user": {"id": 42, "plan": "pro"}, "tags": ["a", "b"]}');
TypeBehavior
jsonStores exact text, re-parses on every query
jsonbStores parsed binary — faster to query, supports indexing (preferred default)

Querying & Indexing JSON

-- -> returns JSON (keep chaining into nested objects), ->> returns text
SELECT payload -> 'user' ->> 'plan' FROM events;      -- returns: pro
SELECT payload -> 'tags' -> 0 FROM events;             -- "a"
SELECT payload #>> '{user,plan}' FROM events;          -- path shorthand

-- @> containment: "does this JSON contain this structure?"
SELECT * FROM events WHERE payload @> '{"user": {"plan": "pro"}}';

-- GIN index needed for @>, ?, ?&, ?| to use an index at all
CREATE INDEX idx_payload_gin ON events USING GIN (payload);
-- or index one specific path if that's the main query pattern
CREATE INDEX idx_payload_plan ON events ((payload -> 'user' ->> 'plan'));
Rule of thumb: JSON for the truly variable-shaped part of a row (metadata, settings, raw API payloads); real columns for anything you query, filter, join, or constrain regularly — once buried in JSON, you lose foreign keys, type checking, and most query-planner optimization.

Safe Schema Migrations on Large Tables

Certain schema changes lock the table while they run — harmless on a small table, a production outage on a live one with millions of rows.

-- Adding a column with a default: Postgres 11+ stores it as metadata
-- instead of rewriting every row, so this is now cheap. MySQL/older
-- engines can still pay the full-rewrite cost.
ALTER TABLE orders ADD COLUMN status text DEFAULT 'pending';

-- Adding NOT NULL still locks + validates every row in one breath —
-- split it instead:
ALTER TABLE orders ADD CONSTRAINT status_not_null
  CHECK (status IS NOT NULL) NOT VALID;      -- instant, no scan yet
ALTER TABLE orders VALIDATE CONSTRAINT status_not_null;  -- scans, lighter lock

-- Adding an index on a live table:
CREATE INDEX CONCURRENTLY idx_orders_status ON orders(status);
-- slower than a plain CREATE INDEX, but doesn't block reads/writes

NOT VALID adds the rule now (fast) and enforces it on new writes immediately, but skips checking existing rows. VALIDATE CONSTRAINT is the second pass — scans existing rows and flips the constraint to validated, failing with the offending row if one violates it.

General pattern for risky migrations: add new columns/indexes unconstrained first, deploy, backfill in small batches (never one giant UPDATE), then add the constraint. Check what your migration tool (Rails, Django, pg-osc/gh-ost) already handles safely.

Level 4 or below is safe to run on a live table without the app noticing — that's the entire reason the NOT VALID/VALIDATE CONSTRAINT split and CONCURRENTLY exist: they trade a slower migration for zero visible impact. Level 5+ stalls writes; level 8 stalls reads too.

Concurrent Transactions on the Same Row

Different rows run fully in parallel. Same-row writes: every UPDATE/DELETE/INSERT implicitly locks the row it touches — a second concurrent write blocks until the first commits or rolls back.

  • Read Committed — the blocked transaction wakes up, re-reads the now-committed value, and applies its update on top. No error, just a pause.
  • Repeatable Read / Serializable — the blocked transaction's snapshot predates the commit, so it gets a serialization failure instead — abort and retry.

Under MVCC (Postgres/MySQL), reads never block writes and writes never block reads — a reader just sees whatever snapshot its isolation level allows.

Replication Basics

A replica is a live copy fed continuously from the primary — for read scaling and failover/durability.

-- Postgres: check replication status from the primary
SELECT client_addr, state, sent_lsn, replay_lsn,
       sent_lsn - replay_lsn AS lag_bytes
FROM pg_stat_replication;

The primary streams its write-ahead log (WAL in Postgres, binlog in MySQL) to each replica, which replays it. This is async by default — the primary doesn't wait for a replica to confirm before committing.

Async (default)Sync
Write latencyFast — doesn't waitSlower — waits for replica ack
Data loss risk on primary failureSmall window possibleNone
Replica stalenessAlways possibleNot for the synchronous replica(s)
A replica is, by definition, always reading a slightly stale snapshot — no isolation level set on the primary changes that. Writing to the primary then immediately reading from a replica can read your own write as if it never happened. Common fixes: route reads-right-after-a-write back to the primary, use synchronous replication (Postgres: synchronous_commit), or alert on lag_bytes/lag time directly.
