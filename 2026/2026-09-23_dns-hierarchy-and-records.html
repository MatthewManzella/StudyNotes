DNS: Hierarchy, Records, and Name Servers

2026-09-23  |  Networking roadmap: TCP/IP → HTTP → TLS → DNS → REST vs gRPC

Resolution Chain

DNS turns example.com into an IP; no single server knows everything, so the lookup is a chain of "ask someone who knows more".

Client/browser → Recursive resolver → Root server → .com TLD server → Authoritative server
  • Root: "who handles .com?" → points to TLD servers
  • TLD: "who handles example.com?" → points to its name server
  • Authoritative: returns the actual IP

TTL and Caching

Resolver caches the answer for the record's TTL; repeat lookups skip the chain.

DNS changes "propagate" slowly because old cached answers linger until their TTL expires.

Records Within the Hierarchy

Each level (root, .com, example.com) is a zone — just a set of records. What differs is which types live where.

ZoneMostly stores
RootNS records, one set per TLD ("who runs .com")
.com TLDNS records, one set per registered domain ("who runs example.com")
example.com (authoritative)A, AAAA, CNAME, MX, TXT — the real answers
  • Different record type = same walk, different question at the last hop (e.g. MX instead of A)
  • MX answer is a hostname (e.g. mail.example.com) → second lookup walks the hierarchy again to get its IP
Hierarchy = chain of NS delegations; A/MX/TXT only live at the zone that's authoritative for the name.

Glue Records

Solve the circularity when a domain's name server lives inside the domain (e.g. ns1.example.com for example.com).

  • TLD server stores the name server's IP alongside the NS delegation
  • Resolver gets the IP without a separate lookup

Structural Rules

  • Exactly one SOA record per zone, at the apex — root, .com, and example.com each have their own
  • CNAME can't coexist with other records at the same name and can't sit at a zone apex → domain root is normally A/AAAA

Name Servers

Any server that answers DNS questions from stored zone records — root, TLD, and authoritative servers are all name servers.

Authoritative name serverRecursive resolver
RoleHolds the official records for a zone — source of truthWalks root → TLD → authoritative on your behalf and caches the result
Authoritative for anything?Yes, its zoneNo
ExamplesCloudflare, Route 53, registrar-runISP resolver, 8.8.8.8, 1.1.1.1
  • A domain typically lists 2–4 NS records for redundancy — resolvers try the next if one is down
  • Owning a domain and running its name servers are separate; connected only by NS records

Where Name Servers Live

  • Root: 13 logical addresses (a–m.root-servers.net), run by 12 organizations; anycast puts the same IP at hundreds of locations → well over 1,500 physical instances
  • TLD: run by the registry (Verisign for .com/.net, Public Interest Registry for .org); also anycast
  • Authoritative: wherever the domain owner chose — registrar (GoDaddy, Namecheap), DNS provider (Cloudflare, Route 53, Google Cloud DNS), or self-hosted
Higher up the hierarchy = more standardized and globally replicated; lower down = wherever that company hosts its DNS.

Transport and Security

  • UDP port 53 by default (no handshake); falls back to TCP for responses too big for one UDP packet
  • DNSSEC: cryptographic signatures on records — integrity/authenticity only, no encryption
  • DoH / DoT: encrypts the lookup itself; plain DNS is sent in the clear

Worked Example: www.example.com

  1. Laptop asks a recursive resolver
  2. Resolver asks root → .com TLD → example.com's authoritative server
  3. "What's the IP" = an A record lookup
  4. www is probably a CNAME to example.com, which then gets its own A lookup
  5. Resolver caches the result for the TTL
  6. Browser gets 93.184.216.34, then continues with the HTTP/TLS/TCP flow
