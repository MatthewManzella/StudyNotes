Indexing & Query Plans

Why Indexes Exist

An index is a sorted B-tree structure that lets the database jump to matching rows instead of scanning every row.

CREATE INDEX idx_users_email ON users(email);
-- WHERE email = 'x@y.com' now binary-searches (O(log n)) instead of scanning (O(n))
Not free: every INSERT/UPDATE/DELETE has to update every index on the table too, and each index costs disk space — indexing everything slows down writes.

Reading a Query Plan

EXPLAIN ANALYZE shows whether the database actually used an index.

EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'x@y.com';
Plan nodeMeaning
Seq Scan / Table ScanNo index used — full scan (bad on large tables)
Index ScanUses the index to find rows, then fetches them
Index Only ScanEverything needed is in the index — no trip to the table

Composite Indexes — Order Matters

An index on (last_name, first_name) supports a leftmost-prefix query — not a query on first_name alone.

CREATE INDEX idx_name ON users(last_name, first_name);

-- Uses the index:
WHERE last_name = 'Smith'
WHERE last_name = 'Smith' AND first_name = 'Jane'

-- Does NOT use it:
WHERE first_name = 'Jane'

When an Index Won't Help

  • Wrapping the column in a function: WHERE UPPER(email) = 'X' (unless a matching functional index exists)
  • Leading wildcard search: LIKE '%smith' (trailing wildcard 'smith%' is fine)
  • Low-selectivity columns (e.g. a boolean is_active — half the table matches either way, so the optimizer may just scan)

Clustered vs. Non-Clustered Indexes

Clustered = the physical row order on disk (one per table). Non-clustered = a separate structure with a pointer back to the row (many per table).

-- Clustered (often the PK) — table rows physically sorted by id
-- Non-clustered — separate lookup structure
CREATE INDEX idx_email ON users(email);  -- non-clustered

A non-clustered lookup needs a second trip (a "bookmark"/"key" lookup) from the index entry back to the row — still far better than a full scan, but slower than clustered.

ClusteredNon-Clustered
ProsFastest range/by-key lookup (data is sorted in place); no extra storage structureMany per table; cheaper to create/rebuild; narrower, fits more in cache
ConsOnly one per table; expensive inserts if the key isn't sequential (page splits on random UUIDs); rebuild reorders the whole tableExtra "bookmark lookup" trip for large result sets (unless covering); extra storage; every write maintains it
Use casesPK/auto-increment lookups, range queries (date BETWEEN ...), append-only log tablesAny filter/join column that isn't the clustering key; multiple access patterns; unique constraints that aren't the PK

Covering Indexes

Includes every column the query needs, so there's no second trip to the table — this is what "Index Only Scan" means.

-- Non-covering: index only has last_name, still fetches email/signup_date from the table
CREATE INDEX idx_name ON users(last_name);

-- Covering: everything the query needs is in the index
CREATE INDEX idx_name_covering ON users(last_name) INCLUDE (email, signup_date);
-- (Postgres/SQL Server syntax — MySQL: just add the columns to the composite index)
Rule of thumb: cluster on whatever column drives your main range/sequential access pattern (often an auto-incrementing PK); add non-clustered indexes for other filter/sort columns; reserve covering indexes for hot, frequently-run queries — wider index = more disk space and slower writes, same tradeoff as any index.
