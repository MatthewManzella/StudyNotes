Advanced Joins & Set Operations

Self Joins

Join a table to itself to compare rows within it — one level, no recursion needed.

SELECT e.name AS employee, m.name AS manager
FROM employees e
JOIN employees m ON e.manager_id = m.id;

Anti-Joins & Semi-Joins

Anti-join = "find rows with no match." Semi-join = "filter by existence, don't fetch the other table's columns."

-- Anti-join, pattern 1: LEFT JOIN + IS NULL
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- Anti-join, pattern 2: NOT EXISTS — often faster, clearer intent
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);

-- Semi-join: filter by existence only, no join columns returned
SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id AND o.amount > 1000);
Rule of thumb: prefer NOT EXISTS over a third option, NOT IN, which has NULL-handling gotchas in the subquery. Prefer a semi-join (EXISTS) over JOIN ... DISTINCT when you only care whether at least one match exists — it can't produce duplicate rows.

Set Operations

Combine full result sets (same column count/types), not just rows within a join.

OperatorBehavior
UNIONRows from both sides, deduplicated (costs a distinct pass)
UNION ALLRows from both sides, duplicates kept — faster
INTERSECTOnly rows present in both sides
EXCEPT (MINUS in Oracle)Rows in the first side but not the second
Rule of thumb: default to UNION ALL unless you specifically need deduplication — UNION's automatic distinct pass is a real, often-forgotten performance cost.

Join Algorithms & Execution Plans

The optimizer picks one of three join algorithms based on table sizes, indexes, and whether data is already sorted — visible in EXPLAIN ANALYZE as Nested Loop, Hash Join, or Merge Join.

AlgorithmHow it worksBest when
Nested LoopFor each row in the outer table, scan the inner table for matches — O(n×m)One side is small, or there's an index on the inner table's join column
Hash JoinBuild a hash table from the smaller side, probe it while scanning the larger side — O(n+m)Large tables, no useful index (default choice); needs enough memory to hold the hash table
Merge JoinWalk both sorted inputs in parallel like a zipperBoth sides are already sorted on the join column (e.g. via an index or ORDER BY)
EXPLAIN ANALYZE
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id
WHERE o.order_date > '2026-01-01';
Seeing a Hash Join where fast index usage was expected often signals a missing index on the join column — or the table's small enough that a full scan + hash beat an index lookup. The optimizer's choice leans on table statistics, so stale stats after a bulk load are a classic, sneaky cause of a sudden bad plan.

Table Statistics

-- Postgres
ANALYZE orders;
ANALYZE;  -- all tables

-- MySQL
ANALYZE TABLE orders;

-- SQL Server
UPDATE STATISTICS orders;

Postgres autovacuum and MySQL/SQL Server auto-update normally keep statistics fresh on their own. The one time to run it manually: right after a bulk load (a big COPY/INSERT all at once) — auto-triggers haven't fired yet and the optimizer is working off stale/empty stats.

Forcing a Join Algorithm

-- Postgres: disable the algorithms you don't want (session-level, not per-query)
SET enable_hashjoin = off;
SET enable_mergejoin = off;
-- ... run query, then reset:
SET enable_hashjoin = on;
SET enable_mergejoin = on;

-- SQL Server: inline hint
SELECT * FROM orders o JOIN customers c ON o.customer_id = c.id
OPTION (LOOP JOIN);  -- or HASH JOIN, MERGE JOIN

-- MySQL 8+ / Oracle: hints in a comment block
SELECT /*+ NO_HASH_JOIN(o, c) */ * FROM orders o JOIN customers c ON o.customer_id = c.id;
Rule of thumb: the optimizer's cost-based decision is usually right, and it re-evaluates as stats/volume change — a hardcoded hint doesn't. If it's picking a bad algorithm, ask why first (stale stats, missing index, genuinely small table) and fix that; reach for a hint only as a temporary diagnostic.
