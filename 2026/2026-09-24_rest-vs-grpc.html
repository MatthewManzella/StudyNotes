REST vs gRPC

2026-09-24  |  Networking roadmap: TCP/IP → HTTP → TLS → DNS → REST vs gRPC

REST

Architectural style, not a protocol: resources addressed by URL, manipulated with standard HTTP methods, usually JSON.

GET    /users/42   fetch
POST   /users      create
PUT    /users/42   replace
DELETE /users/42   remove
  • Reuses HTTP machinery: status codes, caching headers
  • Any HTTP client works (curl, browser, Postman)

gRPC

Remote procedure calls — call a function that runs on another machine.

  • Protocol Buffers: methods and data shapes defined in a .proto file up front; tooling generates typed client/server code
  • Binary over HTTP/2: compact encoding + multiplexing
  • Native streaming: client→server, server→client, or both

  • gRPC extras: built-in deadlines, cancellation, load-balancing hooks
  • gRPC cons: HTTP/2 requirement can trip up older infrastructure

Defining a gRPC Service

You write the .proto (the contract) and the method bodies; protoc writes the classes, serialization, and plumbing in between.

syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}

message GetUserRequest { int32 id = 1; }

message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
Each field's unique number — not its name — is what protobuf uses on the wire.

Who Does What (Todo Service)

StepWhoWhat
1. Write todo.protoYouService + message definitions
2. Run compilerTool: protocprotoc --python_out=. --grpc_python_out=. todo.proto
3. Generated codeAuto-generatedtodo_pb2.py (message classes); todo_pb2_grpc.py (TodoServiceStub + TodoServiceServicer base class)
4. ServerYouExtend the servicer, implement method bodies
5. ClientYouCall the stub
6. TestTool: grpcurlCall the running server directly
# Server — you write
class TodoServicer(todo_pb2_grpc.TodoServiceServicer):
    def CreateTodo(self, request, context):
        return todo_pb2.Todo(id=1, title=request.title, done=False)

server = grpc.server(futures.ThreadPoolExecutor())
todo_pb2_grpc.add_TodoServiceServicer_to_server(TodoServicer(), server)
server.add_insecure_port('[::]:50051')
server.start()
server.wait_for_termination()

# Client — you write
channel = grpc.insecure_channel('localhost:50051')
stub = todo_pb2_grpc.TodoServiceStub(channel)
response = stub.CreateTodo(todo_pb2.CreateTodoRequest(title="Learn gRPC"))

# Test with grpcurl
grpcurl -plaintext -d '{"title":"Learn gRPC"}' localhost:50051 TodoService/CreateTodo

stub.CreateTodo(...) reads like a local call; underneath it serializes to binary, sends over HTTP/2, and deserializes the reply.

Stub vs Servicer

The compiler generates message classes, a client stub, and a server servicer base class — not two stubs.

PieceSideYou…
StubClientCall it, like a remote function
Servicer (base class)ServerExtend and implement it
Both codebases compile the same .proto and get the full output; each side only uses the half relevant to its role in that call. A service can be client for some calls and server for others.

Streaming

rpc ListUsersInOrg (OrgRequest) returns (stream User);

The single word stream makes it a server-streaming call — server sends many User messages over one connection.

Testing and Debugging gRPC

  • grpcurl: curl for gRPC; with server reflection, works without the local .proto
  • Postman / Insomnia: import .proto or use reflection
  • Interceptors: server-side logging middleware
  • Unit tests: generated server class is a plain typed object — call methods directly, no network
  • Wireshark: decodes gRPC given the .proto
  • Errors: gRPC status codes (NOT_FOUND, INVALID_ARGUMENT…), not HTTP status codes

Project Layout

todo-app/
├── proto/todo.proto        ← you write
├── generated/              ← protoc writes; never edit
│   ├── todo_pb2.py
│   └── todo_pb2_grpc.py
├── server/main.py          ← you write
└── client/main.py          ← you write
  • .proto gets its own top-level folder (one file compiles into many languages)
  • Larger companies keep .proto files in a separate shared repo
  • Committing generated code is debated: some commit it, others regenerate at build time and .gitignore it
Only real constraint: keep generated and hand-written code clearly separated.

Sharing .proto Files Across Services

PatternHow
MonorepoOne shared proto/ folder; each service generates its own code into its own language/folder
Separate proto repoOwn repo; services pull it in (git submodule or build dependency) and compile locally
Schema registrye.g. Buf Schema Registry — .proto as versioned packages (todo/v2)
Never let two services generate code from incompatible versions of the same .proto without a plan — protobuf tolerates old/new field differences only if schemas stay compatible.

What YouTube Uses

  • Externally: REST — YouTube Data API v3, JSON over HTTPS
  • Internally: gRPC's predecessor Stubby / gRPC — high-volume service-to-service traffic (processing, recommendations, ads, moderation, storage)

Video Playback

Neither REST nor gRPC — plain HTTP via adaptive bitrate streaming (DASH for YouTube).

  • Video pre-encoded at multiple qualities, chopped into small segments
  • Player fetches a manifest of qualities and segment URLs, then one HTTP GET per segment
  • Weak connection → next segment requested at a lower quality URL, no renegotiation
  • RTMP/RTMPS: ingestion side — creator software pushing video up to be transcoded into DASH segments
REST/gRPC are for small structured request/response exchanges; video is bulk sequential binary data.
