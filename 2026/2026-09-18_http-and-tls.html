Statelessness and cookies

Server sends Set-Cookie: session=abc123; browser auto-attaches Cookie: session=abc123 to future requests to that domain — how "logged in" persists on a stateless protocol.

HTTP/1.1 vs HTTP/2 vs HTTP/3

VersionKey change
HTTP/1.1 (1997)Persistent connections, but requests handled one at a time in order — head-of-line blocking
HTTP/2 (2015)Multiplexed requests over one TCP connection, binary framing, header compression
HTTP/3 (2022)Replaces TCP with QUIC (over UDP) — one lost packet only stalls its own stream, not all of them

TLS guarantees

Wraps TCP in three properties before any HTTP data flows.

  • Confidentiality — encryption prevents snooping
  • Integrity — tampering is detectable
  • Authentication — verifies you're talking to the real server

TLS 1.3 handshake

One round trip: ClientHello (cipher suites + public key share) → ServerHello + certificate → both sides derive the same shared secret independently → symmetric key encrypts everything after.

Asymmetric crypto is only used long enough to safely agree on a symmetric key — symmetric encryption handles the actual data because it's far faster.

Certificates and chain of trust

A Certificate Authority (CA) signs a certificate binding a public key to a domain. Browser trusts a small set of root CAs and verifies the chain down to the server's cert — broken chain or domain mismatch triggers the "connection is not private" warning.

SNI, session resumption, forward secrecy

  • SNI — client states the target hostname during the handshake, before encryption starts, so a server hosting many HTTPS domains on one IP knows which cert to present.
  • Session resumption — reusing previously negotiated keys skips most of the handshake on a revisit.
  • Forward secrecy — a fresh key per session means a stolen long-term private key can't decrypt past sessions.

Kerberos vs TLS (aside)

Different trust models, not competing versions of the same thing.

TLSKerberos
Trust modelCA chain, works with no prior relationship — public internetShared trust with a KDC in advance — closed network (e.g. Active Directory)
Proves identity ofMainly the serverBoth user and service (mutual)
LayerTransport (secures the pipe)Authentication/application (regardless of pipe encryption)
They stack together in enterprise setups: SPNEGO/Negotiate lets a browser attach a Kerberos ticket in the Authorization header, typically over an HTTPS connection — TLS secures the connection, Kerberos proves who's on it.
