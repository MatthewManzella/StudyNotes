Transactions & ACID

A transaction groups statements into one atomic unit — everything happens, or nothing does.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
-- or ROLLBACK; if something went wrong
  • Atomicity — all statements succeed, or all roll back
  • Consistency — the database moves between valid states (constraints/FKs stay intact)
  • Isolation — concurrent transactions don't see each other's uncommitted changes (tunable)
  • Durability — once committed, it survives a crash

Concurrency Phenomena

  • Dirty read — reading another transaction's uncommitted change; if it rolls back, you read data that never existed
  • Non-repeatable read — re-reading the same row in one transaction gives a different value because another transaction committed a change in between
  • Phantom read — re-running the same range query returns a different set of rows because another transaction inserted/deleted a matching row in between

Defaults: Read Committed is the default in Postgres, SQL Server, Oracle. MySQL/InnoDB defaults to Repeatable Read — and its Repeatable Read is stronger than the SQL standard (prevents most phantoms via next-key locking), unlike Postgres's, which relies on snapshot isolation instead.

Locking, Briefly

  • Pessimistic locking — SELECT ... FOR UPDATE locks the row until commit; safe, but blocks others
  • Optimistic locking — no lock; check a version/timestamp column at commit time and fail if it changed, then retry

Why Not Always Serializable

Serializable guarantees correctness but at real cost: it typically works by detecting conflicts and aborting one transaction, so the application needs retry logic; more isolation means more locking/abort-churn and lower throughput; and most weak-isolation bugs (a dirty read on a page-view counter, a phantom row in an hourly report) simply don't matter for the use case. Reserve it for operations where a race condition would cause real harm (double-spending, overselling inventory).

Declaring Locks

-- Row-level pessimistic lock
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
COMMIT;

-- Postgres variants: FOR SHARE (shared — others can read/share-lock, not write),
-- FOR NO KEY UPDATE, FOR KEY SHARE

-- Table-level (rare, blunt, mostly maintenance)
LOCK TABLE accounts IN EXCLUSIVE MODE;      -- Postgres
LOCK TABLES accounts WRITE;                 -- MySQL

-- Optimistic locking — no lock statement, version it yourself
UPDATE accounts
SET balance = balance - 100, version = version + 1
WHERE id = 1 AND version = 5;
-- 0 rows updated → someone else changed it first, retry in the app

Isolation Level vs. Explicit Locking

Isolation level = a transaction-wide guarantee about what you can see. Explicit locking = actively blocking other transactions from touching specific rows. Reach for an explicit lock when:

  • The isolation level only protects reads, not a read-then-act sequence on the same row (e.g. under Read Committed, "read stock → decide → write" has zero protection on its own)
  • You want blocking instead of Serializable's abort-and-retry behavior
  • You need row-level precision instead of escalating the whole transaction
  • Your engine's isolation level has a known gap (e.g. Postgres Repeatable Read doesn't fully prevent phantoms)
Lock flavor matters: FOR UPDATE is fully exclusive (blocks other readers' locks too); FOR SHARE blocks writers but lets other transactions hold their own shared lock concurrently. Use FOR SHARE when you need to block writes but still allow concurrent reads.

Serializable's Real Implementation Cost

Correctness-wise, Serializable guarantees transactions behave as if run one at a time — but "without locking" isn't quite true:

  • Lock-based engines (SQL Server, MySQL/InnoDB) — implement it with locking under the hood (often range/next-key locks); you didn't write the lock, the engine did
  • Postgres (SSI) — doesn't lock proactively; it tracks read/write dependencies and aborts one transaction with a serialization error if a conflict pattern appears — so the application must catch that error and retry, or the operation just silently doesn't happen
for attempt in range(3):
    try:
        run_transaction()
        break
    except SerializationFailure:
        continue  # retry — without this, Serializable alone doesn't save you

Fold Check-Then-Act Into One Atomic Statement

A cheaper alternative to locking/escalating isolation: collapse "read → decide → write" into a single indivisible statement, so there's no window for another transaction to interleave. Works under plain Read Committed, no lock needed.

-- Inventory decrement — 0 rows affected means already sold out
UPDATE inventory
SET stock = stock - 1
WHERE product_id = 5 AND stock >= 1;

-- View counter — the engine locks the row for the instant the atomic UPDATE takes
UPDATE posts SET view_count = view_count + 1 WHERE id = 5;

-- Seat booking — a UNIQUE constraint makes the insert itself the check
CREATE UNIQUE INDEX idx_unique_seat ON reservations(seat_id);
INSERT INTO reservations (seat_id, customer_id) VALUES ('14B', 42);
-- a second concurrent attempt for the same seat fails with a unique-violation error
Rule of thumb: this only works when the whole check-then-act collapses into one statement — but when it fits, it's cheaper than locking or escalating isolation. Note FOR UPDATE/FOR SHARE can't help the seat-booking case at all: those locks only work on rows that already exist, and the seat row doesn't exist yet before the first insert.

SKIP LOCKED for Job Queues

Multiple workers racing for "the oldest pending job" with plain FOR UPDATE queue up waiting on each other — correct, but kills the parallelism you wanted. SKIP LOCKED lets a worker skip a locked row and grab the next available one instead.

-- Problem: workers block on each other's lock
SELECT id FROM jobs WHERE status = 'pending'
ORDER BY created_at LIMIT 1 FOR UPDATE;

-- Fix: skip locked rows, no waiting, no double-grab
SELECT id FROM jobs WHERE status = 'pending'
ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED;

Lost Updates

No isolation level merges conflicting writes — isolation controls visibility and ordering, not content merging. If two users edit the same document and the second save is a plain UPDATE, the first user's changes are just silently overwritten.

-- A read the doc at version 7; check it's still version 7 before saving:
UPDATE documents
SET content = '', version = version + 1
WHERE id = 5 AND version = 7;
-- 0 rows updated → someone else (B) saved first and bumped the version
-- → the app must show a conflict/merge screen, not silently overwrite
Rule of thumb: a database can detect a lost-update conflict (via a version column) and hand it back to the application, but it can't resolve it — real merging requires application logic or a different model entirely (e.g. CRDTs/operational transforms in collaborative editors).
